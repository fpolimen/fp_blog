The next E: e-services.

It was the vision proposed by HP in the late 90s for the digitalization of Business Services — an ecosystem based on open standards. I still remember the advertising in major airports, far before web services, that few people understood at the time.

It anticipated what today is called the **API Economy**, and it was simply too early.

## The HP e-services stack

The vision was operationalised by HP's software proposition, *HP Netaction*, at the moment when e-services were renamed web services. It included all the ingredients for enabling the ecosystem:

| Component | Role |
|-----------|------|
| **HP E-speak** (later HP Web Services Platform, SOAP) | Communication framework |
| **HP Process Manager** | Orchestration of business services |
| **HP UDDI Registry** | Discovery and exposition of services |
| **HP Application Server** (formerly Bluestone, J2EE) | Micro-service implementation runtime |
| **HP JCA Connector Framework** | Integration of legacy applications |

Looking at that list today is striking. The architecture is essentially what we build now — except that the implementation stack has changed beyond recognition.

## From e-services to web services to APIs

The journey from the HP vision to the current API Economy passed through several distinct phases:

1. **Late 90s — e-services**: open ecosystem, service discovery via UDDI, SOAP over HTTP. Too complex, too early.
2. **2000s — web services**: WS-* standards, WSDL, enterprise service buses. Powerful but heavyweight.
3. **2010s — REST APIs**: lightweight, HTTP-native, JSON. The API Economy begins. Platforms like AWS, Stripe, Twilio make services composable.
4. **2015s onwards — serverless**: functions as the unit of deployment. The provider manages infrastructure, scaling, and availability. The developer ships logic.

Each step reduced friction. Each step moved the focus from infrastructure to business logic.

## Why serverless is the key booster

The serverless model completes the e-services vision in a way that the original stack could not. In a FaaS environment:

- A business service is a **function** — stateless, versioned, composable.
- Discovery happens through API gateways rather than UDDI registries.
- Orchestration is handled by event-driven pipelines rather than process managers.
- Scaling is automatic, billed per invocation, with no idle cost.

The ecosystem HP imagined — where any organisation could expose and consume digital services without managing infrastructure — is finally achievable. The tools are different; the vision is the same.

We are implementing that original architecture today with better tools. The serverless approach is the key enabler that will make it work at scale.
